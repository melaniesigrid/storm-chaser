Three themes, one token contract

No screen knows which theme is active. Every colour, typeface and radius resolves through a named token, so a third theme is a data change rather than a UI change. These three are the app’s. The page runs the same contract on the three wordmark directions instead — Atmospheric, Broadcast and Signage, in the switcher up there — which is the clearest proof the contract holds: the same named tokens, filled from a different set of designs entirely.

Field Card

Twelve stocks, one ink

In Field Card every card is printed on its own stock — a logged storm picks one from its id, a fixed panel from its name — so a card keeps its colour when the column around it is filtered or added to. Six of these was one screenful before the palette repeated, and the first twelve were tinted whites that a phone in daylight read as white. These are stock. Every text colour the theme can draw on them, ink and captions and the tier-coloured score, clears WCAG AA on all twelve, which the theme test holds the whole list to.

Built for the moment you are standing in a field

Everything here answers a question a chaser actually has, at the moment they have it.

The numbers that matter

Temperature and wind, plus the two variables generic weather apps leave out: CAPE and lifted index. Those tell you whether the atmosphere can actually build something.

A Chase Index, not a forecast

A 0 to 100 score blending the observed weather code, gust strength, rainfall rate and both convective indices, with a ranked list of what drove it. Pure, tested, and honest about being a judgement aid.

Photo first, record second

If the image cannot be copied into permanent storage, the report is never written. The log can never contain an entry pointing at a file that is not there.

Weather frozen onto the report

No forecast API serves historical conditions for an arbitrary past timestamp, so the snapshot is copied onto the record at capture time. A report stays readable years later.

Works with no signal

A persisted query cache, an explicit offline banner over the last good reading, and a bundled sample dataset that is always labelled as sample data.

Legible in daylight

Nothing renders below 12px, every tappable control clears 44px, and contrast is a unit test: WCAG AA is asserted across all three themes on every build.

Five tiers, one meaning

The same ladder colours the index meter, the map pins and the report cards. A colour means the same thing everywhere in the app, and each theme only changes its values.

How it is put together

The short answer to “which architectural pattern”: feature-sliced layers with a one-way dependency rule, a repository over storage, and hooks standing between the screens and everything else. The longer answers are below, each one pointing at the file that settles it.

app/
Routes only. A screen composes hooks and components and decides what a person sees; it never talks to storage, never parses a response and never does maths on a reading. Expo Router means the route tree IS the file tree.
src/features/
One slice per domain — weather, storms, location — and every slice is the same four folders: api/ at the wire, model/ for pure domain logic and types, data/ for persistence, hooks/ for the state a screen consumes. Slices do not reach into each other's internals.
src/core/
What every feature shares and no feature owns: the UI primitives, the theme contract, the chart layer, the storage interface, the formatters. Core knows nothing about storms or weather.
src/services/
The outside world that is not a feature: the query client and its persistence, the network probe, the cloud client. Swappable, and stubbed in tests.

The rule that makes it a pattern rather than a folder layout: dependencies point down that list and never back up. Core may not import a feature. A model may not import a component. A screen may not import a repository. The layering is the thing that keeps a four-theme redesign from touching a single line of domain logic.

Where does the business logic live?

In model/, as pure functions. The Chase Index is a number derived from a reading, not a piece of UI state: same input, same score, no clock, no network, no React. That is why most of the suite needs no renderer and runs in milliseconds — the interesting logic was never entangled with a view.

How is state managed?

Split by who owns it. Server state is TanStack Query, keyed by rounded coordinates and persisted, so a cold start with no signal still renders. Owned data goes through a repository. Cross-cutting preferences — theme, profile, onboarding — are small contexts over a key-value store. There is no global store, because no piece of state needed one.

src/services/query/queryClient.tssrc/features/storms/data/StormRepository.tssrc/core/theme/ThemeProvider.tsx

What crosses the boundary from the API?

Nothing in its wire shape. contracts.ts describes what Open-Meteo sends, mappers.ts turns it into the app's own types, and everything above that point works in domain terms. Swapping to weather.gov is a new client and a new mapper, not a change to a screen.

src/features/weather/api/contracts.tssrc/features/weather/model/mappers.ts

Why is the weather copied onto a saved report?

Because no forecast API serves historical conditions for an arbitrary past timestamp. A reference would be a record that degrades; the snapshot is written onto the report at capture time and stays readable years later. The same reasoning orders the write: the photo is copied into permanent storage first, so the log can never hold an entry pointing at a file that is not there.

src/features/storms/model/types.tssrc/features/storms/data/photoStore.ts

What makes the components reusable?

There is one of each. Every card in the app is a Panel, every string is a Text variant, and both read the active theme rather than a colour. No screen knows which theme is running, so a fourth theme is a data change — and a card that wants a colour of its own asks for a tone, which twelve stocks answer in one theme and nothing answers in the other three.

How do you know it holds?

734 tests, and the ones worth naming guard a decision rather than a line: WCAG AA is asserted for every text colour on every surface in every theme, the flash cadence is held under WCAG 2.3.1, and the repository is tested against a substituted store, so persistence is verified without a device.

The stack, all of it

Everything the app is actually built on, and what each piece is doing here. Nothing in this list needs an API key, an account or a paid tier, which is the other reason it was chosen: the whole thing clones and runs.

Runtime

  • React Native React Native 0.86 on React 19
  • Expo Expo SDK 57, Expo Router, camera, location, file system
  • TypeScript Strict, with noUncheckedIndexedAccess
  • Node Metro, the capture scripts, the test runner

Data and device

  • TanStack Query Server state, persisted to survive a cold start
  • AS AsyncStorage Behind a KeyValueStore interface the tests substitute
  • OM Open-Meteo Free, keyless, no account. The only network call
  • react-native-maps Google Maps on Android, Apple Maps on iOS

Interface

  • RA Reanimated Version 4, on the UI thread
  • SV react-native-svg Every chart, mark and weather glyph
  • NativeWind Version 4, over Tailwind 3
  • MC Meteocons Static and Lottie, 60 weather glyphs
  • Google Fonts Bricolage, Anton, Big Shoulders, IBM Plex Mono

Testing and delivery

  • Jest jest-expo. 734 tests over 29 suites
  • ESLint eslint-config-expo, flat config, zero warnings
  • Playwright Every screenshot on this page, from source
  • GitHub Actions Guards the deploy, then publishes it
  • Vercel This page, static, no build step

Marks are drawn from Simple Icons (CC0) and inherit the active theme's ink rather than carrying their own colour, so the row reads as one set. Five pieces have no monochrome mark of their own and get a typographic tile instead of a drawing that only half looks like the real thing.
